# 强化学习演练数据采集

本轮目标为第三问、第四问各 500 个完整全清的真实演练案例。仅使用演练，按原模拟器倒计时等待，不跳过开局限制。安全结束但未全清的案例也保留并标注，计数目标只包含完整全清案例。

## 存放位置

主数据集为单个 SQLite 文件：

`results/practice_batches/rl-dataset-20260911/practice_training.sqlite3`

同目录中的 `practice_training-raw/episodes` 保存逐局原始审计材料，`practice_training-raw/progress.json` 保存当前进度。每局完成后立即事务提交数据库，再原子更新进度；重启采集器会核验已有证据并按案例编号去重。数据库使用 DELETE 日志模式，提交后的持久数据集中在一个 `.sqlite3` 文件中。大型 JSON 采用 zlib 压缩。

这些数据均留在本机并被 Git 忽略。数据库移除了队号、认证字段、原始请求标识及本机路径等信息；原始审计日志可能含队号，单独保存在本地。

## 内容及训练用途

| 表 | 内容 |
|---|---|
| `episodes` | 案例编号、题号、行为策略、代码版本、最终清除统计、质量标记和训练/验证/测试划分 |
| `steps` | 按时间排序的动作、位置、频道、反馈、重试次数、前后状态引用及时间成本 |
| `observations` | 每步之后当时可见的状态；压缩存储一次，下一步复用为前状态 |
| `source_estimates` | 每个干扰源的估计坐标、保守误差半径、清除位置和定位依据 |
| `evidence` | 压缩脱敏后的原始证据及哈希，用于核验 |
| `metadata` | 协议、版本、压缩方式、标签和奖励字段语义 |

最终源数量和最终估计位置属于案例结束后的标签，不加入此前任何一步的观测状态。一个案例完整分配到同一数据分区，按案例哈希进行约 80%/10%/10% 划分，避免相邻步骤分别进入训练集和测试集。

位置标签是数学估计，不是读取模拟器隐藏真值。利用示向度扇区、`near` 的 5 米范围及清除成功的 20 米范围重建保守候选集，并保存包围误差半径。第四问无信号不解释为距离远；各源方向、接收半径和具体类型保持未知。第三问全向类型来自题目公开条件。

为兼顾速度与精度，第三问使用 efficient、第四问使用 triangular，再增加有限的清除前补测：只在附近候选范围仍较大时触发，每个频道最多 2 次、每局最多 32 次，尽量将误差半径减至 5 米。已经收到 near 或达到精度目标时停止补测；第四问补测无信号也停止。所有补测都进入原始动作日志和耗时统计。实际误差上界逐点记录，不保证所有点都达到 5 米。

这批数据适合离线示范学习、观测与动作序列建模、定位评估等。现有强化学习分支是第三问的候选宏动作 PPO，训练需要该策略当时生成的候选特征、动作概率和值估计。这批底层接口轨迹需要后续训练适配，不能直接冒充 PPO 采样；第四问也需要独立适配。随机场景提供场景变化，行为策略的动作覆盖仍有限。

`reward_time_component = -delta_virtual_time_s`，另存 `clear_success` 和移动、换频、检测、光学、清除等成本分量。没有擅自指定组合奖励权重。正常结束与未完成截断应在训练中区别处理，不能把最终完整性标记作为早期策略输入。

## 启动、续采与暂停

保持演练专用模拟器启动并登录，使用已有演练控制器的启动方法。以下命令不会自动登录、接管活动案例或启动正式测试。

```powershell
$env:CUMCM_ROBOT_ID = '你的登录队号'
$db = 'results\practice_batches\rl-dataset-20260911\practice_training.sqlite3'

# 首次采集；后台运行，不需要逐局点击。
.\scripts\collect_practice.ps1 -Q3 500 -Q4 500 -Output $db -Background

# 发生可处理的中断后续采，既有案例按证据去重。
.\scripts\collect_practice.ps1 -Q3 500 -Q4 500 -Output $db -Resume -Background

# 不接触模拟器，只读取进度。
.\.venv-win\Scripts\python.exe -m practice_control.collect --output $db --status
```

试采使用 `-Q3 2 -Q4 2`，随后以 `-Resume -Q3 500 -Q4 500` 扩大目标，试采直接计入数据集。采集进程全程持有安装目录的互斥锁；每次开局至少间隔 5 秒，同时保留模拟器自己的准备与倒计时。

批量采集复用已核验的 WebView 调试连接，避免每个动作都重新发现页面、建立和关闭连接。每次机器人请求前仍实时读取并核验演练题号、案例编号与接口状态，不缓存这些判断；每次调用还检查当前页面来源和标题。连接出错立即丢弃，结果不确定的操作不自动重放。该优化保持搜索策略、精度补测、完整日志和开局倒计时不变。

每局机器人 HTTP 请求也复用固定 `127.0.0.1:2026` 的连接，只允许进入、测量、清除、退出四个接口。传输层每次只发送一次，不跟随重定向；失败时关闭连接，由原客户端保留相同请求编号和请求体进行幂等结果核对，逐动作演练状态检查继续执行。响应大小、严格 JSON 校验和完整日志保持原约束。

在 `practice_training-raw` 目录创建 `STOP` 文件，可让采集器保存当前一局后停止。再次续采前移除该停止标记。未登录、连接故障、案例归属改变、结果不确定或连续 3 局未全清时停止并保存错误，不自动重复开局。数据库目标完成不等于每条位置标签都是精确真值。

对于模拟器明确返回的 `server_timeout` 开局拒绝，只有本次目录仅包含匹配的开局失败证据、并且等待前后都明确确认模拟器空闲且未开放/进入机器人接口时，才允许发起下一次新演练。连续恢复等待为 10、20、40 秒，之后仍失败则停止；每次保留独立记录，失败开局不计入目标。连接断开、响应丢失等结果不确定的操作不适用此恢复机制。进度中的 `errors` 保留历史错误，`recovery_events` 记录恢复过程，当前是否在采集应看 `status` 和计数变化。
