在原4060主机上仅使用一个低优先级CPU进程，不使用GPU。基准与候选交错运行两轮；54个案例包含8个已使用开发案例、32个新普通案例、14个新压力案例，共216次整局运行。以下P95与最大值先对同一案例的两轮取平均，再计算。

|---|---:|---:|---:|
| 平均实际耗时 | 0.605802秒 | 0.419967秒 | 减少30.68% |
| P95实际耗时 | 0.815786秒 | 0.558390秒 | 减少31.55% |
| 最大实际耗时 | 0.879829秒 | 0.607790秒 | 减少30.92% |

## 改了什么

1. 同一轮测量决策中的两轮候选评分共享相同假想几何的精确半径，避免重复裁剪和求最小包围圆。
2. 完整覆盖验证仍生成原来的全部见证点。某个见证点一旦已知不可能提高最终覆盖半径，就停止它剩余的距离计算。
3. 对重复接收圆复用不可变半平面约束，最多缓存128组；原浮点计算和裁剪顺序保持不变。
4. 已有候选区域时，取消随后立即丢弃的默认区域构造。

首阶段不含第3项，独立完整对照降低23.48%。加入第3项后的完整对照降低30.68%。两批分别交错测量原版和候选；不能直接把两批的候选绝对秒数相减，因为机器负载和CPU频率也有变化。

## 时间指标的边界

本次计时包括策略、本地模拟客户端及收尾，排除Python进程启动、模块导入、客户端构造、结果序列化和事后下界计算，也没有真实HTTP等待。它不等于正式结果表中的真实程序端到端时间。

另读了原760版本40局已保存的演练HTTP会话：端到端平均约2.359秒，请求往返约1.184秒，请求之间的程序间隔约1.126秒，响应后状态处理约0.032秒。程序间隔还含客户端、日志和调度；请求往返也含服务端处理，不能称纯网络时间。本轮未运行新版官方演练，因此尚无新版端到端实测；若仅程序间隔同比下降30.68%，粗算约2.014秒，但这只是条件估计，不能填写为比赛成绩。

本轮仅选择可说明等值关系、并通过差分的优化。剩余几何计算仍有开销，接口层也可能有优化空间，但本轮没有对这些方向验证有效方案，不能宣称程序已经达到理论最快。
